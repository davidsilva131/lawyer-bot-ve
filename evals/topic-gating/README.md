# Topic-gating eval set + calibration/regression harness spec

Status: **drafted** by wayfinder ticket [#18](https://github.com/davidsilva131/lawyer-bot-ve/issues/18) (task, agent-driven). The set and spec are the ground truth for the LLM topic gate, the retrieval threshold θ, and the CI regression gate. Label ratification items for the PO are listed in [§9](#9-po-ratification-items-open-for-grilling); `IN_SCOPE_UNANSWERABLE` labels are provisional on corpus scope ([§8](#8-dependencies)).

## 1. Purpose and reliability targets

Per `docs/feasibility-study.md` §4 and `research/topic-gating/findings.md` §3:

- **False-accept < 1%** — answering an off-topic/unanswerable query. Precision-biased product stance: one wrong off-topic answer erodes trust and invites liability; a false rejection costs one retry.
- **False-reject ≤ 10%** — rejecting (or failing to answer) a valid Venezuelan-law query.
- The set measures the **hybrid three-stage pipeline end to end**: deterministic pre-filter → LLM gate → retrieval gate. It is also the source for the embedding/reranker bake-off (`research/llm-stack/findings.md`, before-committing test 1: 200–500 query→relevant-chunk judgment pairs, Recall@5).
- Two distinct reject outcomes are a product requirement (§4.2, §6.4): `OUT_OF_SCOPE` (topic rejection copy) vs `IN_SCOPE_UNANSWERABLE` (coverage-gap copy) — never conflated.

## 2. Files and schema

- `queries.in_scope.jsonl` — 240 queries, 24 Venezuelan law branches × 10.
- `queries.off_topic.jsonl` — 62 queries, 8 off-topic categories.

Record schema (JSONL, one record per line):

| field | type | notes |
|---|---|---|
| `id` | string | `<category>-NN`, unique |
| `category` | string | branch code (in-scope) or off-topic category code |
| `branch` | string | required for in-scope records only |
| `query` | string | Spanish, user register (colloquial, typos, fact patterns, procedural phrasing) |
| `label` | enum | `IN_SCOPE`, `OUT_OF_SCOPE`, `IN_SCOPE_UNANSWERABLE`, `MIXED` |
| `split` | enum | `train`, `calibration`, `eval` (see §4) |
| `po` | bool | optional; `true` = provisional label pending PO ratification (§9) — excluded from targets until ratified |
| `note` | string | optional; decision rationale, policy pointer, or near-domain warning |

## 3. Label taxonomy and routing contract

The pipeline's observable outcome per query must be the expected path (study §4.1/§4.3, §6.4 copy):

| expected label | expected pipeline routing | rejection/answer copy |
|---|---|---|
| `IN_SCOPE` | answer path (retrieval-grounded, with citations) | — |
| `IN_SCOPE_UNANSWERABLE` | rejected as **in-scope but uncovered** (routed through retrieval; empty/short retrieval → unanswerable path) | §6.4 «Su consulta corresponde a materia legal venezolana, pero no dispongo de esa información…» |
| `OUT_OF_SCOPE` | rejected as topic out-of-scope (including deterministic stage-1 hits: greetings/identity) | §6.4 topic-rejection copy (identity/meta variants for stage-1 records) |
| `MIXED` | answer the legal sub-part only (via gate's `legal_subpart`), stating the rest is ignored; on extraction failure → mixed copy §6.4 | §6.4 mixed copy |

Policy anchors baked into the labels (from §4.3, ratified): procedural questions are in scope (they route to retrieval; uncovered → `IN_SCOPE_UNANSWERABLE`, never topic-reject); homework *explanations* are in scope, *deliverable production* is out; meta-prompts/injection are always out of scope + canned copy; language is classified by topic, not language; personalized-advice queries are in scope, answered with the general rule + escalation (per §4.3 edge case 4) — see `advice` records.

## 4. Split policy

- **`train`** (65 records): few-shot exemplars for the LLM gate prompt (2 per in-scope branch + representative `OUT_OF_SCOPE`, `MIXED`, `IN_SCOPE_UNANSWERABLE`). Visible to prompt authors; **never** used for metrics.
- **`calibration`** (125): θ tuning and prompt iteration (see §6). Tuning may use this split freely; reported numbers are calibration estimates, not targets.
- **`eval`** (112): frozen held-out regression set. No tuning decisions ever use it; it is read once per pipeline version for the headline FAR/FRR report and the CI gate.

Every label class is present in every split (`IN_SCOPE_UNANSWERABLE` 2/2/2, `MIXED` 2/4/2, `OUT_OF_SCOPE` 9/21/12, `IN_SCOPE` 52/98/96).

Set statistics (generated by validation at drafting):

| | train | calibration | eval | total |
|---|---|---|---|---|
| in-scope file | 48 | 96 | 96 | 240 |
| off-topic file | 17 | 29 | 16 | 62 |
| **total** | **65** | **125** | **112** | **302** |

In-scope branches (10 each): civil, familia, sucesiones, inmobiliario, contractual, mercantil, penal, procesal penal, procesal civil, laboral, constitucional, administrativo, tributario, aduanero, bancario, seguros, propiedad intelectual, consumidor, agrario, ambiental, migratorio, municipal, electoral, NNA. Off-topic categories: foreign, nonlegal, identity, injection, politics (incl. 2 legal-frame `IN_SCOPE`), homework (2 `IN_SCOPE`, 2 `OUT_OF_SCOPE`, 2 `po`), mixed, advice (8 `IN_SCOPE` w/ escalation).

## 5. Harness design (build-phase contract)

The harness is implemented during the build effort (this repo currently ships the study + map artifacts). Contract:

**Pipeline interface** — the harness drives the real pipeline functions, not mocked scores:
- stage 1: deterministic pre-filter verdict (for identity/meta records);
- stage 2: LLM gate JSON `{in_scope, branch_of_law, legal_subject, legal_subpart, reason}` (temperature 0; `UNCERTAIN` routes to stage 3, never hard-rejects);
- stage 3: retrieval gate — hybrid BM25+dense, top-k=5, cross-encoder re-rank, max-score threshold θ, over the **current corpus snapshot**.

**Outputs/report** (per run, JSON + human table): per-record routing vs expected routing; per-class routing accuracy; parse/schema rate of stage 2; `UNCERTAIN` rate; FAR/FRR with 95% Wilson intervals; corpus snapshot hash + θ value + prompt/config hash.

**Metrics (formal):**
- routing accuracy per class: fraction of records whose observed routing equals the expected routing (§3).
- `FAR = # records with expected label ∈ {OUT_OF_SCOPE, IN_SCOPE_UNANSWERABLE} observed on the answer path ÷ # such records` — target **< 1%** on `eval`.
- `FRR = # records with expected label IN_SCOPE observed on any reject path ÷ # IN_SCOPE records` — target **≤ 10%** on `eval`.
- `MIXED` correctness: observed routing ∈ {legal-subpart answer, mixed copy}; topic-reject of a `MIXED` record counts as a false-reject for product purposes (reported separately).
- stage-2 diagnostics (tracked on `calibration`, informational): JSON parse rate (≥ 98%), `UNCERTAIN` rate, gate-level per-class accuracy. **Never** threshold the LLM gate's self-reported confidence (research §3).

## 6. θ calibration procedure

1. Run stage-3 retrieval over the corpus snapshot for all `calibration` records (frozen query text, no translations).
2. Sweep θ over the post-re-rank max score (monotone lattice, e.g. 10⁻⁴…0.9 log-spaced + article-number fast-path exemption kept on).
3. For each θ compute hybrid routing on `calibration` (stage 1 + 2 verdicts cached from the current prompt; stage 3 verdict from the sweep) → calibration FAR/FRR.
4. **Selection rule:** smallest θ with calibration FAR < 1% (precision bias); among ties, smallest FRR. Record the chosen θ, date, corpus snapshot hash, and prompt hash in the gating config.
5. **Infeasibility rule:** if no θ reaches FAR < 1% at FRR ≤ 40% on calibration, θ alone cannot carry the gate — tighten the LLM gate (rubric/exemplars on the `train` subset) or the reranker tier (`research/llm-stack` upgrade path), then re-sweep. Never ship an operating point that misses the FAR target.
6. **Re-calibration triggers:** any corpus addition (new Gaceta/TSJ texts), embedding/reranker change, or LLM-gate prompt change. Re-run §6.1–6.5, then re-report on `eval`.

## 7. Regression gate and CI wiring

Wiring lands with the build (codebase home is an open build-charting item — the contract below is codebase-agnostic and follows AGENTS.md conventions: English, no financial data in CI logs).

- **Trigger:** every PR touching the gate prompt, gating config (including θ), corpus ingest scripts/snapshot, or the eval set itself; plus a scheduled nightly run on the default branch.
- **Failure conditions (block merge):** `eval` FAR ≥ 1% or FRR > 10%; stage-2 parse rate < 98% (calibration, informational warning only); harness environment breakage.
- **Corpus-change label review:** a PR that adds corpus documents must re-verify `IN_SCOPE_UNANSWERABLE` labels (coverage may have moved) and re-run §6; label updates land in the same PR — the CI compares the corpus snapshot hash against the hash recorded at labeling time and fails if they disagree without a label-review note.
- **`po: true` records** are excluded from target computation until ratified (§9); their routing is reported separately.
- **Report:** PR comment with the metrics table + JSON artifact; nightly failures page the maintainer (ops detail at build time).
- Production rejects are sampled for human review and may graduate into the set (identity of the source is not recorded in the set).

## 8. Dependencies

- **#21 corpus ingestion design** — decides the launch corpus scope; `IN_SCOPE_UNANSWERABLE` labels (6 records) are provisional on it. Procedural-code coverage gaps and the Código Civil digitization status (study §6.1) may flip labels.
- **#16 stack research** (resolved) — bake-off test 1 consumes this set for Recall@5 on real Spanish legal chunks; gate models Gemini Flash vs Groq Llama 3.3 70B are proven on this set (test 4).
- **#22 backend architecture** — harness lives in the shared core (§7 of the study).

## 9. PO ratification items (open for grilling)

These were deliberately **not** decided at drafting; they surface as grilling inputs (map #15 gating–adjacent tickets or the build-phase grilling):

1. **Homework gray zone** (`hw-05`, `hw-06`, provisional labels): where the resumen/estructura → entregable line sits for summaries of rulings and simulated courtroom exercises.
2. **Politics with a legal frame** (`pol-01`, `pol-03`): confirm the aggressiveness of the constitutional-frame criterion (in scope only with an explicit legal question).
3. **Personalized-advice convention** (`advice` × 8): ratified policy is general-rule + escalation (§4.3); confirm the eval-label convention (labeled `IN_SCOPE`).
4. **Corpus-gap labels**: ratification that `IN_SCOPE_UNANSWERABLE` follows the *launch* corpus scope and that the §7 label-review procedure is the update path.
5. **Multi-turn coverage**: the set is single-turn by design (policy §4.3); ask whether a multi-turn subset is required before launch or deferred to post-launch growth.

## 10. Maintenance

- Adding records: append to the category's file with the next id; assign `split` by §4 balance (keep every label in every split); never edit an `eval` record's label in a PR that also tunes the prompt (tuning on eval invalidates it — such changes require a note in the PR body).
- Relabeling: a label change is a decision; record the reason in `note` and reference the source (issue/ADR).
- Validation: `queries.*.jsonl` parse cleanly, ids unique, enums valid — run the repo's validation script at build time (contract in §5).
